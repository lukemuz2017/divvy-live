Divvy commute: how the data moves

Each person saves named routes and activates one at a time. The app recommends where to pick up and drop off a bike on that route, favoring full pick-up stations and empty drop-off stations. Planned before any code was written, then updated when saved routes were added.

What each part sends, and what breaks if it changes

HandoffWhat it sendsIf this changes or fails
Divvy to workerBikes, e-bikes and docks per station, plus renting and returning flagsIf Divvy renames a field, the worker must fail its run instead of saving blanks. The page then shows Down instead of bad advice.
Worker to databaseOnly stations whose counts or flags changed, plus one row in worker_runsIf the comparison includes last_reported, about 1,100 stations look changed instead of 92 over 3 minutes, and Realtime messages run out much faster.
Database to RealtimeEach changed rowRealtime needs the table added, read access and a row-level security policy. If one is missing, the page freezes with no error.
Realtime to pageNew counts for a station near the active route, and each new run rowA dropped connection can miss updates, so the page reloads current rows when it reconnects.
Page to server route to CensusTyped addresses, returned as coordinatesIf Census is down, nobody can save a new route. Routes already saved keep working.
Clerk to SupabaseA token saying who is signed inIf this breaks, row-level security finds no matching person and saved routes come back empty.

How the page decides what to show

Pick-up points

10 × bikes ÷ (bikes + docks). The station must be renting and have at least 1 bike.

Drop-off points

10 × docks ÷ (bikes + docks). The station must be accepting returns and have at least 1 dock.

Stale

The newest worker run is over 3 minutes old. The browser checks this on its own clock, because a stopped worker sends nothing. Recommendations are hidden.

Down

The newest worker run failed. Recommendations are hidden.
